## 重点内容

### ⭐⭐⭐ 核心概念
- **需求分析五原则**：表示和理解信息域、定义软件功能、表示软件行为、划分模型层次、从要素到细节
- **信息域三要素**：信息内容、信息流、信息结构
- **需求建模的四种方法**：实体关系图、数据流图、状态转换图、用况图

### ⭐⭐ 重要知识点
- **需求协商的组织因素**：不一致目标、责任转移、组织文化、管理态度、部门差异
- **需求建模的目的**：用简洁、准确、结构清晰的方式描述需求，着重于"做什么"而非"怎么做"
- **需求建模的主要方法**：结构化分析方法（SA）、面向对象的分析方法（OOA）

### ⭐ 基本原则
- 需求分析原则是所有分析方法共同遵循的操作基础
- 需求协商不仅是技术争论，还涉及组织和行政因素
- 模型应描述系统"做什么"而非"如何做"

## 详细笔记

### 一、需求分析原则

> 📚 **课本出处**：第3章 3.3.1节"需求分析原则"

关于需求分析过程的具体实现，研究人员已经开发了若干方法，不同的分析方法有自己独特的观点。然而，这些分析方法都遵循一组操作原则：

1. **必须能够表示和理解问题的信息域**
2. **必须能够定义软件将完成的功能**
3. **必须能够表示软件的行为**（作为外部事件的结果）
4. **必须划分描述数据、功能和行为的模型**，从而可以分层次地揭示细节
5. **分析过程应该从要素信息移向细节信息**

💡 **理解技巧**：这五条原则构成了需求分析的"操作框架"——前两条关注数据和功能（做什么），第三条关注行为（怎么响应），后两条关注组织方法（怎么分层、怎么深入）。

通过应用这些原则，分析人员将能系统地处理问题：
- 检查**信息域**可以更完整地理解功能
- 通过**模型**可以更简洁地交流功能和行为的特征
- 应用**抽象与分解**可减少问题的复杂度

### 二、信息域

> 📚 **课本出处**：第3章 3.3.2节"信息域"

所有软件开发最终的目的都是为了处理数据，即将一种形式的数据转换成另一种形式的数据。信息域包括**信息内容**、**信息流**以及**信息结构**三个组成部分。

#### 1. 信息内容

信息内容表示了单个数据和控制对象，目标软件所有处理的信息集合由它们构成。

**示例**：数据对象"工资"是一组重要数据的组合：

| 属性 | 说明 |
|:----:|:-----|
| 领款人姓名 | 员工标识 |
| 净付款数 | 实际发放金额 |
| 付款总额 | 发放前总金额 |
| 扣除额 | 各项扣款合计 |

- 需要创建"工资"的内容以确定它所需的**属性定义**
- 控制对象"系统状态"的内容可以由一个位串定义
- 数据和控制对象还可以与其他数据和控制对象**关联**

#### 2. 信息流

信息流表示了数据和控制在系统中流动时的**变化方式**。

```mermaid
flowchart LR
    A[输入对象] --> B[中间变换]
    B --> C[中间信息]
    C --> D[进一步变换]
    D --> E[输出]

    style A fill:#e3f2fd
    style E fill:#e8f5e9
```

- 输入对象被变换为**中间信息**（数据和/或控制）
- 然后进一步被变换为**输出**
- 数据的变换是程序必须完成的**功能或子功能**
- 在两个变换（功能）间流动的数据和控制定义了每个功能的**接口**

#### 3. 信息结构

信息结构表示了各种数据和控制项的**内部组织形式**。需要回答的问题包括：

- 数据或控制项将被组织为$n$维表还是**树形结构**？
- 在结构的语境内，什么信息是和其他信息**相关**的？
- 信息包含在单个结构中，还是使用**不同的结构**？
- 在某信息结构中的信息如何与另一个结构中的信息**相关**？

💡 **理解技巧**：信息域的三个要素可以这样记忆——"内容"告诉你数据有什么，"流"告诉你数据怎么走，"结构"告诉你数据怎么组织。三者缺一不可。

### 三、需求协商

> 📚 **课本出处**：第3章 3.3.3节"需求协商"

复杂的系统有许多项目相关人员，他们之间的需求必定会出现冲突。协商的过程就是**讨论需求冲突，找出每个人都满意的折衷方案**。

⚠️ **常见误区**：协商不是简单的逻辑或技术上的争论，经常会被组织和行政的考虑或当事人的个性所左右。

#### 需求协商中的组织和行政因素

| 因素 | 说明 | 注意事项 |
|:----:|:-----|:---------|
| ①不一致的目标 | 组织中不同岗位的人的个人目标不可能与组织目标完全一致 | 要设法发现个人目标下隐含的需求 |
| ②责任的丧失或转移 | 开发软件可能把权力从一个部门转移到另一个部门 | 丧失权力的人可能提出不可能实现或代价很高的需求 |
| ③组织文化 | 各部门互相竞争时，不同部门提出的需求可能用于提升竞争优势 | 注意部门间的竞争关系 |
| ④组织管理态度和士气 | 经历裁员的组织中，人可能敌视管理者 | 可能故意为需求获取设置障碍 |
| ⑤部门差异 | 与大多数部门有显著差异的部门有不同的文化 | 该部门的需求可能受其独特文化影响 |

#### 冲突解决会议

通常会议是解决冲突最快的方式，分为**3个阶段**：

```mermaid
flowchart LR
    A[叙述阶段] --> B[讨论阶段]
    B --> C[决策阶段]

    style A fill:#e3f2fd
    style B fill:#fff3e0
    style C fill:#e8f5e9
```

- 会议的参加者应包括能发现冲突、遗漏或重叠的**分析员**，以及能解决被发现问题的**项目相关人员**
- 所有冲突的需求都应该**单独讨论**
- 不能假定关于某项需求的决定会对相关需求同样有效

### 四、需求建模

> 📚 **课本出处**：第3章 3.3.4节"需求建模"

创建模型是需求分析阶段的重要活动。模型以一种**简洁、准确、结构清晰**的方式系统地描述了软件需求。

#### 建模的目的和作用

| 作用 | 说明 |
|:----:|:-----|
| 理解系统 | 帮助分析员理解系统的信息、功能和行为 |
| 促进交流 | 使需求分析任务更容易实现，结果更系统化 |
| 发现问题 | 易于发现用户描述中的模糊性和不一致性 |
| 评审依据 | 模型将成为复审的焦点，确定规约的完整性、一致性和精确性 |
| 设计基础 | 为设计者提供软件要素的表示视图 |
| 沟通工具 | 在分析人员和用户之间建立更便捷的沟通方式 |

#### 建模的核心原则

> ⭐ **核心重点**：所创建的模型要着重于描述系统**要做什么**，而不是**如何去做**。目标软件的需求模型不应涉及软件的实现细节。

通常分析人员使用**图形符号**来创建模型，将信息、处理、系统行为和其他相关特征描述为各种可识别的图形符号，同时在图形符号旁边辅助以**文字描述**。

#### 常用的建模方法

目前已存在的多种需求分析方法引用了不同的分析策略，常用的分析方法有以下几种：

**1. 实体关系图（ERD）**

- 关注系统的**数据模型**
- 描述系统中的数据对象及其之间的关系
- 常用于数据库设计和信息建模
- 属于面向数据的建模方法

**2. 数据流图（DFD）**

- 关注系统的**功能模型**
- 描述数据在系统中的流动和变换过程
- 面向数据流的结构化分析方法（SA）的核心工具
- 第5章将详细介绍

**3. 状态转换图（STD）**

- 关注系统的**行为模型**
- 描述系统对外部事件的响应和状态变化
- 适用于有明显状态转换特征的系统

**4. 用况图（Use Case Diagram）**

- 关注系统的**功能和交互**
- 描述系统与外部执行者之间的交互
- 面向对象分析方法（OOA）的核心工具
- 第8章将详细介绍

> 💡 **理解技巧**：四种建模方法从不同角度描述系统——ERD看"数据有什么"，DFD看"数据怎么变"，STD看"系统怎么变"，用况图看"谁和系统怎么交互"。

其中，结构化的分析方法和面向对象的分析方法应用非常广泛，具有较好的发展潜力。

## 总结

### 五条需求分析原则

1. 表示和理解问题的信息域
2. 定义软件将完成的功能
3. 表示软件的行为（外部事件的结果）
4. 划分描述数据、功能和行为的模型，分层次揭示细节
5. 分析过程从要素信息移向细节信息

### 信息域三要素

| 要素 | 关注点 | 核心问题 |
|:----:|:------:|:---------|
| 信息内容 | 数据是什么 | 数据对象有哪些属性？ |
| 信息流 | 数据怎么流动 | 输入如何变换为输出？ |
| 信息结构 | 数据如何组织 | 数据项之间的组织关系？ |

### 四种建模方法对比

| 建模方法 | 模型类型 | 关注点 | 适用场景 | 对应方法 |
|:--------:|:--------:|:------:|:---------|:---------|
| 实体关系图（ERD） | 数据模型 | 数据对象及关系 | 数据库设计、信息建模 | 面向数据 |
| 数据流图（DFD） | 功能模型 | 数据流动与变换 | 业务流程、功能分解 | 结构化分析（SA） |
| 状态转换图（STD） | 行为模型 | 状态变化与事件响应 | 有状态特征的系统 | 结构化分析 |
| 用况图（UCD） | 功能交互模型 | 执行者与系统交互 | 功能需求描述 | 面向对象分析（OOA） |

### 需求协商的五个组织因素

不一致目标 -> 责任转移 -> 组织文化 -> 管理态度 -> 部门差异

### 关键要点

1. **五条原则**是所有分析方法的共同基础
2. **信息域分析**是需求分析的起点，理解数据是理解功能的前提
3. **需求协商**需要同时关注技术和组织因素，技术争论容易解决，组织冲突往往更棘手
4. **建模的核心**是描述"做什么"而非"怎么做"，模型不涉及实现细节
5. 不同建模方法从不同角度描述系统，实际项目中常常**组合使用**多种方法

## 疑问与思考

### ❓ 待解决问题
1. 四种建模方法（ERD/DFD/STD/用况图）各自适用于什么场景？如何选择？
2. 信息域的三个要素（信息内容、信息流、信息结构）之间有什么区别？

### 💡 解答
1. **ERD（实体关系图）**适用于数据密集型系统，如需要设计数据库、梳理实体间关系的场景（如电商系统的商品、订单、用户之间的关系）。**DFD（数据流图）**适用于业务流程密集型系统，关注数据如何被加工和传递，如银行交易处理、工资计算等数据变换过程。**STD（状态转换图）**适用于有明显状态变化特征的系统，如电梯控制、订单状态流转（待支付->已支付->已发货->已完成）等。**用况图**适用于需要从用户视角描述系统功能边界的场景，适合在项目初期与用户沟通功能范围。实际项目中常常组合使用：用况图定义功能边界，DFD描述业务流程，ERD建模数据结构，STD描述关键对象的状态行为。
2. 三者的核心区别：**信息内容**回答"数据是什么"——描述单个数据对象包含哪些属性（如"工资"对象由领款人姓名、净付款数、付款总额、扣除额组成）。**信息流**回答"数据怎么走"——描述数据在系统中如何从输入经过变换到达输出（如用户输入订单数据->系统计算总价->输出发票）。**信息结构**回答"数据怎么组织"——描述数据项之间的组织关系，是树形、表状还是其他形式，以及不同结构之间的关联。简记：内容=数据的"组成"，流=数据的"路径"，结构=数据的"骨架"。

### 💡 个人理解/技巧
- 五条原则可以按"数据->功能->行为->组织->深入"的逻辑链条记忆
- 信息域的三个要素分别对应建模方法：信息内容对应ERD，信息流对应DFD，信息结构对应数据结构设计
- 需求协商中最容易忽视的是"组织管理态度和士气"，这个因素隐蔽但影响巨大
- 建模方法的选择应该基于项目特点：数据密集型系统优先ERD，流程密集型优先DFD，交互密集型优先用况图
