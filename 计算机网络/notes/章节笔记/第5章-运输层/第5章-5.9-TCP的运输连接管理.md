### 二、TCP的连接建立（三报文握手）⭐⭐⭐

![用三报文握手建立TCP连接](../../../images/fa7b5382a6b5e50772c60476a9f69e5ef13b36e7c578ec05d44bed5d8839f9be.jpg)

#### 握手过程详解

**初始状态：**

- A（客户）：CLOSED
- B（服务器）：CLOSED → 创建TCB → LISTEN

**第一次握手（SYN）：**

- A向B发送连接请求报文段
- **SYN = 1**，**seq = x**（初始序号）
- 不能携带数据，但要消耗一个序号
- A进入 **SYN-SENT**（同步已发送）状态

**第二次握手（SYN + ACK）：**

- B收到请求，如同意建立连接，向A发送确认
- **SYN = 1**，**ACK = 1**
- **seq = y**（B的初始序号）
- **ack = x + 1**（确认收到A的SYN）
- 不能携带数据，但要消耗一个序号
- B进入 **SYN-RCVD**（同步收到）状态

**第三次握手（ACK）：**

- A收到B的确认后，向B给出确认
- **ACK = 1**
- **seq = x + 1**
- **ack = y + 1**（确认收到B的SYN）
- 可以携带数据，如果不携带数据则不消耗序号
- A进入 **ESTABLISHED**（已建立连接）状态
- B收到A的确认后也进入 **ESTABLISHED** 状态

#### 为什么需要三次握手？

**防止已失效的连接请求报文段突然又传送到B，产生错误。**

**异常场景：**

1. A发出第一个连接请求，但在网络中长时间滞留
2. A重传连接请求，建立连接，传输数据，释放连接
3. 第一个连接请求在连接释放后才到达B
4. B误认为是新的连接请求，发送确认
5. **如果没有第三次握手：** B发出确认后连接就建立了，但A不会理睬，B的资源被浪费
6. **有了第三次握手：** A不会向B的确认发出确认，B收不到确认，就知道A没有要求建立连接

### 三、TCP的连接释放（四报文握手）⭐⭐⭐

![TCP连接释放的过程](../../../images/79ddc42d628ebf90534175ffadf2bb3d20bb1ec5e2f66ec50e7f8b13895363d7.jpg)

#### 释放过程详解

**初始状态：** A和B都处于 **ESTABLISHED** 状态

**第一次挥手（FIN）：**

- A的应用进程通知TCP释放连接
- A发送连接释放报文段
- **FIN = 1**，**seq = u**（前面已传送数据的最后一个字节序号+1）
- 即使不携带数据，也消耗一个序号
- A进入 **FIN-WAIT-1**（终止等待1）状态

**第二次挥手（ACK）：**

- B收到释放报文段后发出确认
- **ACK = 1**，**seq = v**，**ack = u + 1**
- B进入 **CLOSE-WAIT**（关闭等待）状态
- **半关闭状态**：A到B方向的连接释放，但B到A方向的连接未关闭
- A收到确认后进入 **FIN-WAIT-2**（终止等待2）状态

**第三次挥手（FIN + ACK）：**

- B如果没有数据要发送，应用进程通知TCP释放连接
- B发送连接释放报文段
- **FIN = 1**，**ACK = 1**，**seq = w**，**ack = u + 1**
- B进入 **LAST-ACK**（最后确认）状态

**第四次挥手（ACK）：**

- A收到B的连接释放报文段后发出确认
- **ACK = 1**，**seq = u + 1**，**ack = w + 1**
- A进入 **TIME-WAIT**（时间等待）状态
- B收到确认后进入 **CLOSED** 状态

#### TIME-WAIT状态（2MSL）⭐⭐⭐

**MSL（Maximum Segment Lifetime）**：最长报文段寿命，RFC 793建议为2分钟

**A在TIME-WAIT状态必须等待2MSL的原因：**

1. **保证A发送的最后一个ACK报文段能够到达B**
   - 如果ACK丢失，B会超时重传FIN + ACK
   - A在2MSL时间内收到重传的FIN + ACK
   - A重传ACK，重新启动2MSL计时器
   - 最后A和B都正常进入CLOSED状态
2. **防止已失效的连接请求报文段出现在本连接中**
   - 经过2MSL，本连接持续时间内产生的所有报文段都从网络中消失
   - 下一个新连接中不会出现旧的连接请求报文段

**注意：** B结束TCP连接的时间比A早一些

### 四、保活计时器（Keepalive Timer）

**场景：** 客户与服务器建立TCP连接后，客户端主机突然出故障

**机制：**

- 服务器每收到一次客户数据，重新设置保活计时器（通常2小时）
- 若2小时没有收到客户数据，发送探测报文段
- 以后每隔75秒发送一次探测报文段
- 若一连发送10个探测报文段后仍无响应，关闭连接

### 五、TCP的有限状态机 ⭐⭐⭐

![TCP的有限状态机](../../../images/5b019e98245990a2fd8f504585b308b047fd70130adcc356c91198e5bc749491.jpg)

#### 11种状态

| 状态              | 英文    | 说明                   |
| --------------- | ----- | -------------------- |
| **CLOSED**      | 关闭    | 没有连接                 |
| **LISTEN**      | 收听    | 等待连接请求               |
| **SYN-SENT**    | 同步已发送 | 已发送SYN，等待确认          |
| **SYN-RCVD**    | 同步收到  | 收到SYN，发送SYN+ACK，等待确认 |
| **ESTABLISHED** | 已建立   | 连接已建立，可以传送数据         |
| **FIN-WAIT-1**  | 终止等待1 | 已发送FIN，等待确认          |
| **FIN-WAIT-2**  | 终止等待2 | 收到ACK，等待对方的FIN       |
| **CLOSE-WAIT**  | 关闭等待  | 收到FIN，发送ACK，等待应用关闭   |
| **CLOSING**     | 关闭中   | 同时关闭                 |
| **LAST-ACK**    | 最后确认  | 已发送FIN，等待最后的ACK      |
| **TIME-WAIT**   | 时间等待  | 等待2MSL               |

#### 状态转换说明

- **粗实线箭头**：客户进程的正常变迁
- **粗虚线箭头**：服务器进程的正常变迁
- **细线箭头**：异常变迁

### ⭐⭐⭐ 三次握手 vs 四次挥手

| 对比       | **三次握手（建立连接）** | **四次挥手（释放连接）**       |
| -------- | -------------- | -------------------- |
| **目的**   | 建立连接，同步序号      | 释放连接，关闭双向通道          |
| **报文段数** | 3个             | 4个                   |
| **控制位**  | SYN, ACK       | FIN, ACK             |
| **特殊情况** | 第二次可拆成两个       | 第二次和第三次不能合并（可能有数据传输） |

### ⭐⭐⭐ 关键序号和确认号变化

**三次握手：**

```
A → B: SYN=1, seq=x
B → A: SYN=1, ACK=1, seq=y, ack=x+1
A → B: ACK=1, seq=x+1, ack=y+1
```

**四次挥手：**

```
A → B: FIN=1, seq=u
B → A: ACK=1, seq=v, ack=u+1
B → A: FIN=1, ACK=1, seq=w, ack=u+1
A → B: ACK=1, seq=u+1, ack=w+1
```

## 疑问与思考

### ❓ 疑问1：连接建立用三次握手，而连接释放却要四次挥手，为什么不对称？

💡 **解答**：

- TCP是**全双工**的，两个方向的数据传输独立进行
- **三次握手**时：B收到A的SYN后，可以将SYN和ACK**合并**在一个报文段中发送（因为B此时没有数据要发送，同意连接的同时就能同步自己的序号）
- **四次挥手**时：A发送FIN表示不再发送数据，但B可能还有数据要发送。B收到FIN后先发ACK确认，等B的数据发送完毕后再发FIN。由于B的ACK和FIN之间可能间隔一段时间（B还要继续传数据），所以**不能合并**，必须分成两个报文段
- 核心原因：**连接建立时双方都同意即可，连接释放时双方可能各有不同节奏**

### ❓ 疑问2：如果第三次握手的ACK报文段丢失了，会怎样？

💡 **解答**：

- A发送第三次握手的ACK后进入ESTABLISHED状态，可以正常发送数据
- 如果这个ACK丢失，B没有收到确认，**B停留在SYN-RCVD状态**，不会进入ESTABLISHED
- A此时已认为连接建立，可能开始发送数据
- B收到A的数据报文段（其中ACK=1），可以从中确认连接建立，从而进入ESTABLISHED状态
- 如果A在超时时间内未发送数据，B会超时重传SYN+ACK（第二次握手的报文段）
- A收到重传的SYN+ACK后，会重新发送ACK确认，B最终也能进入ESTABLISHED

### ❓ 疑问3：TIME-WAIT状态等待2MSL是否可以缩短？SYN洪泛攻击是什么？

💡 **解答**：

- **2MSL的作用**：课本指出RFC 793建议MSL为2分钟，即TIME-WAIT需等待4分钟。实际上现代网络MSL通常远小于此值（如30秒），TCP允许不同实现根据具体情况使用更小的MSL值
- **TIME-WAIT的两个理由**（课本原文）：
  1. 保证A发送的最后ACK能到达B（如果ACK丢失，B会重传FIN+ACK，A需在2MSL内收到并重传ACK）
  2. 防止已失效的旧连接报文段出现在新连接中（2MSL后旧报文段从网络中消失）

- **SYN洪泛攻击**（课本未详述，属拓展知识）：
  - 攻击者向服务器**大量发送SYN报文段**，但不回复第三次握手的ACK
  - 服务器为每个半开连接分配资源（TCB），**SYN-RCVD状态的连接大量积累**
  - 服务器资源耗尽，无法响应正常用户的连接请求
  - **防御措施**：SYN Cookie技术（服务器不立即分配资源，而是用算法编码连接信息到序号中，收到第三次握手后才分配资源）

### ❓ 疑问4：TCP有限状态机中的CLOSE-WAIT状态如果一直不关闭会怎样？

💡 **解答**：

- CLOSE-WAIT状态表示B已收到A的FIN并确认，但B的应用进程还没有通知TCP释放连接
- 如果B的应用程序存在**bug**（如忘记调用close()），B会**一直停留在CLOSE-WAIT状态**，不会发送自己的FIN
- 这会导致连接无法正常释放，A一直等待在FIN-WAIT-2状态
- 这就是所谓的**连接泄漏**，是实际网络编程中常见的问题
- 保活计时器（Keepalive Timer）可以在一定程度上检测到对端已不活跃，最终关闭连接

### 💡 个人理解

- 三次握手的核心目的是**双方同步初始序号**（SYN），而不仅仅是"确认对方存在"。三次是因为需要A对B的确认再做一次确认，防止已失效的旧SYN报文段导致B误建连接
- 四次挥手体现了TCP全双工的特性：每个方向的关闭是独立的，任何一方都可以在关闭自己的发送通道后继续接收对方的数据
- TCP有限状态机是理解连接管理的关键：粗实线代表客户端的正常路径，粗虚线代表服务器的正常路径，细线代表异常变迁
- SYN洪泛攻击利用了三次握手中"服务器先分配资源"的弱点，SYN Cookie是经典的无状态防御方案
- CLOSE-WAIT状态的连接泄漏是实际工程中需要特别注意的，可通过监控系统中该状态连接的数量来发现

## 总结

### 三次握手（建立连接）vs 四次挥手（释放连接）

| 对比项 | **三次握手（建立连接）** | **四次挥手（释放连接）** |
|:------:|:----------------------:|:----------------------:|
| **目的** | 建立连接，同步双方初始序号 | 释放连接，关闭双向通道 |
| **报文段数** | 3个 | 4个 |
| **控制位** | SYN, ACK | FIN, ACK |
| **发起方** | 客户（主动打开） | 任何一方均可发起 |
| **能否合并** | B的SYN+ACK可合并（第2次） | B的ACK与FIN不能合并（可能有数据要发） |
| **额外等待** | 无 | 主动关闭方需等待2MSL（TIME-WAIT） |
| **状态数** | 3个新状态（SYN-SENT, SYN-RCVD, ESTABLISHED） | 6个新状态（FIN-WAIT-1/2, CLOSE-WAIT, CLOSING, LAST-ACK, TIME-WAIT） |
| **消耗序号** | SYN报文段各消耗1个序号 | FIN报文段各消耗1个序号 |

### TCP连接建立与释放流程对比

| 步骤 | 三次握手（建立连接） | 四次挥手（释放连接） |
|:----:|:-------------------:|:-------------------:|
| 第1步 | A→B: SYN=1, seq=x | A→B: FIN=1, seq=u |
| 第2步 | B→A: SYN=1,ACK=1, seq=y,ack=x+1 | B→A: ACK=1, seq=v, ack=u+1 |
| 第3步 | A→B: ACK=1, seq=x+1,ack=y+1 | B→A: FIN=1,ACK=1, seq=w,ack=u+1 |
| 第4步 | — | A→B: ACK=1, seq=u+1,ack=w+1 |

### TCP有限状态机 -- 各状态要点

| 状态 | 英文 | 触发条件 | 关键说明 |
|:----:|:----:|:--------:|:--------:|
| **CLOSED** | 关闭 | 初始/最终状态 | 无连接存在，TCB未创建 |
| **LISTEN** | 收听 | 服务器创建TCB后 | 被动等待客户连接请求 |
| **SYN-SENT** | 同步已发送 | 客户发送SYN后 | 等待服务器的SYN+ACK |
| **SYN-RCVD** | 同步收到 | 服务器收到SYN并回复SYN+ACK | 等待客户的第三次ACK |
| **ESTABLISHED** | 已建立 | 三次握手完成 | 连接已建立，可双向传送数据 |
| **FIN-WAIT-1** | 终止等待1 | 主动方发送FIN后 | 等待对方对FIN的ACK |
| **FIN-WAIT-2** | 终止等待2 | 收到对方对FIN的ACK | 等待对方发送FIN |
| **CLOSE-WAIT** | 关闭等待 | 被动方收到FIN并发送ACK | 半关闭状态，等待本方应用关闭 |
| **CLOSING** | 关闭中 | 双方同时发送FIN | 特殊情况：同时关闭 |
| **LAST-ACK** | 最后确认 | 被动方发送FIN后 | 等待对方对FIN的最后ACK |
| **TIME-WAIT** | 时间等待 | 主动方发送最后的ACK | 等待2MSL后进入CLOSED |

### 核心要点

1. **三次握手的必要性**：防止已失效的旧连接请求报文段到达服务器，导致服务器误建连接并浪费资源
2. **四次挥手的必要性**：TCP全双工，每个方向独立关闭；被动方的ACK和FIN不能合并（可能还需继续发送数据）
3. **TIME-WAIT的2MSL**：(1) 保证最后的ACK能到达对方；(2) 等待网络中旧连接的报文段消失，防止干扰新连接
4. **半关闭状态**：四次挥手的第2、3步之间，A→B方向已关闭，但B→A方向仍可传输数据
5. **保活计时器**：2小时无数据则发送探测报文，每75秒一次，连续10次无响应则关闭连接
6. **SYN洪泛攻击**：大量发送SYN但不完成第三次握手，耗尽服务器资源；防御方法包括SYN Cookie等
